# HTTPS con nginx en el puerto 443

**8 de septiembre de 2026.** Petición del usuario: «vamos a ponerle certificados SSL a la
plataforma y se le asociará un DNS… cambiar el puerto 9090 que se usa por el 443». El
nombre DNS será **plataforma.ejemplo.local**; el DNS y el certificado definitivo los
gestiona otro proceso. Aquí: nginx, el 443 y la seguridad.

## Arquitectura

```
navegador ──HTTPS 443──▶ nginx (terminación TLS) ──HTTP 127.0.0.1:9090──▶ waitress (Flask)
navegador ──HTTP 80───▶ nginx ── 301 ──▶ https://<mismo nombre o IP>/…
```

- **nginx 1.18** (paquete de Ubuntu 22.04) escucha en 80 y 443, hace la terminación TLS y
  reenvía a la aplicación. Configuración: `/etc/nginx/sites-available/omniguard` (copia en
  el proyecto: `deploy/nginx/omniguard.conf`); el sitio `default` se retiró.
- **waitress** escucha SOLO en `127.0.0.1:9090` (ajuste `webui_host`). Desde la red, el 9090
  ya no responde: comprobado con `curl` («conexión rechazada»).
- El servicio `threat-intel-webui` no cambia de usuario ni de endurecimiento
  (`NoNewPrivileges`, `ProtectSystem`): el 443, que es privilegiado, lo abre nginx.
- Las cabeceras de seguridad (`Content-Security-Policy` estricta, `X-Frame-Options`,
  `X-Content-Type-Options`, `Referrer-Policy`) las sigue poniendo la aplicación y pasan tal
  cual; nginx no las duplica, para que haya una sola fuente.

## Certificado

Instalado el 8 de septiembre de 2026 a las 13:02, en sustitución del temporal autofirmado
(borrado). Ruta acordada, propietario `root:root`, **fuera** del proyecto para que el usuario
`si` y la aplicación no puedan leer la clave:

```
/etc/ssl/inteligencia-amenazas/plataforma.crt   PEM, 3 certificados: servidor + intermedio + raíz   644
/etc/ssl/inteligencia-amenazas/plataforma.key   PEM, clave privada RSA 4.096 sin contraseña       600
/etc/ssl/inteligencia-amenazas/ca.crt            raíz «DigiCert Global Root G2»                     644
```

| Dato | Valor |
|---|---|
| Sujeto | `CN=*.ejemplo.local`, O=Jefa del Proceso C y Cia S.A, L=Bogota, C=CO |
| Nombres (SAN) | `*.ejemplo.local`, `ejemplo.local` (cubre `plataforma.ejemplo.local`; **no** cubre la IP) |
| Emisor | DigiCert Global G2 TLS RSA SHA256 2020 CA1 → DigiCert Global Root G2 (CA pública) |
| Validez | 29 de diciembre de 2025 → **29 de enero de 2027** |
| Clave | RSA 4.096 bits; la clave privada casa con el certificado (misma huella de clave pública) |
| Cadena | verificada con `openssl verify` contra el almacén del sistema: `OK` |

Los ficheros llegaron con propietario de un usuario de dominio y la **clave privada en
644** (legible por cualquier usuario del equipo): lo primero que se hizo fue `chown
root:root` y `chmod 600`.

Comprobaciones tras recargar nginx: `openssl s_client -servername plataforma.ejemplo.local`
devuelve la cadena completa (profundidad 0-2) y `Verify return code: 0 (ok)`; `curl` **sin**
`-k` a `https://plataforma.ejemplo.local/login` (resolviendo el nombre a la IP) responde
`200` con `ssl_verify_result=0`, es decir, un navegador que confía en DigiCert no avisa de
nada. Entrar por `https://10.10.11.10` sigue funcionando pero **con aviso de nombre**, porque
la IP no está en el certificado: en cuanto el DNS resuelva, se entra por el nombre.

### HSTS

Activado el mismo día (`Strict-Transport-Security: max-age=31536000`), porque el emisor es
una CA pública en la que confían todos los navegadores. Los navegadores ignoran HSTS para
direcciones IP, así que el acceso por IP con aviso sigue siendo posible.

### Vigilancia de la caducidad

La plataforma vigila el certificado como vigila la contraseña SMTP (`threatintel/certificado.py`):

- **Administración → Credenciales**: tarjeta «Certificado HTTPS» con días restantes, nombre,
  emisor, fecha de caducidad y fichero (hoy: 143 días, DigiCert Inc, 29/01/2027).
- **`/salud.json`** (Zabbix): `ti.certificado.estado` (0 vigente, 1 por caducar, 2 caducado,
  3 sin leer) y `ti.certificado.dias_restantes`. El estado global pasa a «atención» cuando
  está por caducar y a «crítico» cuando ha caducado.
- **Correo de administración** en la ejecución diaria cuando quedan `tls_aviso_dias` (30) o
  menos, una vez por semana (`admin_notices`, tipo `tls_expiry`); con asunto de acción
  requerida si ya caducó.
- Ajustes: `tls_certificado_ruta` y `tls_aviso_dias` (grupo Interfaz). Solo se lee el
  certificado público; la clave privada no se toca.

### Renovar (cada enero)

```bash
sudo cp plataforma.crt plataforma.key /etc/ssl/inteligencia-amenazas/
sudo chown root:root /etc/ssl/inteligencia-amenazas/plataforma.*
sudo chmod 600 /etc/ssl/inteligencia-amenazas/plataforma.key
sudo chmod 644 /etc/ssl/inteligencia-amenazas/plataforma.crt
openssl x509 -in /etc/ssl/inteligencia-amenazas/plataforma.crt -noout -subject -dates -ext subjectAltName
sudo nginx -t && sudo systemctl reload nginx
```

El `.crt` debe llevar la cadena intermedia detrás del certificado del servidor, en ese orden,
y la clave sin contraseña. Si llega un `.pfx`: `openssl pkcs12 -in fichero.pfx -clcerts -nokeys
-out plataforma.crt` y `openssl pkcs12 -in fichero.pfx -nocerts -nodes -out plataforma.key`
(la contraseña, en un fichero con permisos 600, nunca en el chat).

Cuando el nombre DNS resuelva: cambiar `webui_url` (Administración → Ajustes) a
`https://plataforma.ejemplo.local`, que es lo que llevan los enlaces de los correos.

## Cambios en la aplicación

| Ajuste (Administración → Ajustes) | Valor hoy | Qué hace |
|---|---|---|
| `webui_host` | `127.0.0.1` | waitress escucha solo en el propio equipo |
| `webui_https` | activo | cookie de sesión con `Secure`; enlaces con `https` (`PREFERRED_URL_SCHEME`) |
| `webui_tras_proxy` | activo | la dirección real del cliente se toma de la cabecera que pone nginx, **un solo salto** |
| `webui_url` | `https://10.10.11.10` | dirección pública para los correos; pasará al nombre DNS |

Cómo llega la dirección real a la auditoría, y por qué antes estaba mal:

- Hasta hoy `webui/auth.py`, `webui/vistas/sesion.py` y `webui/vistas/remediaciones.py`
  leían la cabecera `X-Forwarded-For` **tal cual, sin proxy delante**: cualquier cliente
  podía enviarla y falsear la dirección que queda en la auditoría. Ahora todos usan
  `request.remote_addr`.
- Con `webui_tras_proxy`, `crear_app` envuelve la aplicación con `ProxyFix(x_for=1,
  x_proto=1, x_host=1, x_port=1)` y waitress se arranca con `trusted_proxy="127.0.0.1"`,
  `trusted_proxy_count=1` y las cuatro cabeceras `X-Forwarded-*` como confiables. Sin lo
  segundo no funcionaba: waitress descarta por omisión las cabeceras de proxy de cualquier
  origen no declarado (`clear_untrusted_proxy_headers`), y la auditoría seguía registrando
  `127.0.0.1` aunque nginx enviara la dirección real.
- nginx envía `X-Forwarded-For $remote_addr` (no `$proxy_add_x_forwarded_for`): lo que el
  cliente escriba en esa cabecera se descarta, no se concatena. Comprobado: un intento de
  acceso con `X-Forwarded-For: 203.0.113.9` queda auditado con la dirección real.

Pruebas: `tests/test_proxy_inverso.py` (sin proxy la cabecera se ignora; con proxy se toma
la de nginx y solo un salto; cookie `Secure` y esquema `https`; los tres ajustes visibles en
Administración).

## Verificación adversaria (tarde del 8 de septiembre) y endurecimiento

Tres revisores independientes de solo lectura (nginx y TLS; confianza en el proxy dentro de
la aplicación; ficheros y vigilancia del certificado) y un refutador por hallazgo. Resultado:
14 hallazgos confirmados (2 medios, 12 bajos), 1 refutado, 13 informativos, y 39 puntos
verificados como correctos (cadena completa, cifrados, HSTS en todas las respuestas, 9090
cerrado a la red, cabeceras de la aplicación intactas, dirección real en la auditoría, sin
restos del certificado temporal, clave 600 de root). Todo lo confirmado quedó corregido:

| Gravedad | Hallazgo | Corrección |
|---|---|---|
| MEDIO | Los registros `omniguard.access.log` y `.error.log` nacieron con 644 root:root (IP y rutas de navegación del SOC legibles por cualquier cuenta local; el equipo tiene 11 cuentas con intérprete) | `chown www-data:adm` y `chmod 640`; logrotate ya crea los nuevos con 640 (diario, 14 días, comprimidos). Comprobar el 10 de septiembre que los rotados salen con 640 |
| MEDIO | La rotación aún no se había ejecutado y la documentación no describía los registros | Apartado «Registros» más abajo |
| MEDIO | El análisis de la fecha de openssl usaba `strptime` con `%b`: dependía del idioma de Python y fallaría en silencio con un idioma en español | `ssl.cert_time_to_seconds` (independiente del idioma); prueba que fija `LC_TIME` en español |
| BAJO | El 80 redirigía a `https://<cualquier Host>` (redirección abierta por Host) y el 443 entregaba a la aplicación cualquier Host | Lista blanca: solo `plataforma.ejemplo.local` y `10.10.11.10`; cualquier otro Host se corta sin respuesta (`444`) en el 80 y en el 443 |
| BAJO | `X-Forwarded-Host`/`-Port` aplicados por ProxyFix: vía de inyección de Host si alguna vista generara direcciones absolutas | `ProxyFix(x_host=0, x_port=0)` y waitress solo confía en `X-Forwarded-For` y `X-Forwarded-Proto`; nginx fija el Host él mismo. Prueba con Host reenviado falso |
| BAJO | `gzip on` heredado: páginas autenticadas con el token CSRF comprimidas (superficie BREACH) sin beneficio en red local | `gzip off` en el bloque 443 |
| BAJO | Cuerpos mayores de 41 MB y caídas de waitress mostraban la página por defecto de nginx (inglés, sin CSP); la aplicación no tenía manejador 413 | `error_page 413 502 503 504` → `/var/www/omniguard/error.html` en español, sin estilos ni scripts, con HSTS y CSP; `@app.errorhandler(413)` en la aplicación con su prueba |
| BAJO | Con `webui_url` definido, los correos de credenciales y de fuentes perdían su ruta profunda; el ajuste no se validaba | `config.url_publica(cfg, ruta)` como único constructor de enlaces (siete módulos); `webui_url` debe empezar por `https://` (o `http://`), sin espacios ni barra final |
| BAJO | `tls_certificado_ruta` se pasaba a openssl sin validar y cada lectura podía costar hasta 10 s | Solo rutas absolutas con `.crt`/`.pem`/`.cer` y fichero regular; resultado en memoria por (ruta, fecha de modificación) durante 60 s; validación también al guardar el ajuste |
| BAJO | «Sin certificado» y «no se pudo leer» no cambiaban el estado global de `/salud.json` | Pasan a «atención» con su motivo |
| BAJO | La tarjeta «Fichero» recortaba la ruta y no se veía el nombre | Nombre del fichero como valor y directorio en la nota |
| BAJO | Pruebas sin cubrir: primer certificado de la cadena, idioma, `X-Forwarded-Proto`/`Host` falsos, `SameSite` | Añadidas (`tests/test_certificado.py`, `tests/test_proxy_inverso.py`) |

Refutado (no se cambió): «no hay comprobación de coherencia entre `webui_tras_proxy`,
`webui_host` y `webui_https`»; es cierto que no la hay, pero cada combinación incoherente
falla de forma visible (el servicio no arranca o el navegador no llega), y la ayuda de cada
ajuste dice exactamente qué requiere. Informativos aceptados: sin OCSP stapling (el
certificado no lo exige y la salida a Internet está restringida), la raíz de DigiCert viaja
en la cadena (inofensivo), y cualquier proceso local del servidor podría falsear la
dirección auditada (inherente a confiar en 127.0.0.1).

## Nombre canónico y redirección desde la IP (14:10; activada a las 14:13)

**Estado final**: el usuario pidió forzarla sin esperar al DNS del servidor
(`omniguard-activar-redireccion --forzar`, 14:13). Desde entonces **toda petición a la IP
responde `301` hacia `https://plataforma.ejemplo.local`** (comprobado: `http://10.10.11.10/…`,
`https://10.10.11.10/…?x=1` y `http://omniguard…` → `301` al nombre con la ruta y los
parámetros conservados; el nombre → `200` con TLS válido; Host ajeno → cortado). El
temporizador quedó desactivado y la configuración anterior está en
`/etc/nginx/sites-available/omniguard.anterior-2026-09-08-1413`. Mientras el DNS de un puesto
no resuelva el nombre, ese puesto no puede entrar ni por la IP ni por el nombre; la vuelta
atrás es la orden `cp` de abajo más `nginx -t` y `systemctl reload nginx`.


A petición del usuario: `webui_url` pasó a **`https://plataforma.ejemplo.local`** (los enlaces
de los correos ya van al nombre) y **toda petición a la IP debe redirigir al nombre**.

El DNS corporativo (10.10.11.1) **todavía no resolvía el nombre** en ese momento. Activar la
redirección antes de que resuelva dejaría a todo el mundo fuera (la IP redirige a un nombre
que el navegador no encuentra), así que:

- La configuración está **preparada y validada** en
  `/etc/nginx/sites-available/omniguard.redireccion-al-nombre` (copia en
  `deploy/nginx/omniguard.redireccion-al-nombre.conf`): el 80 redirige siempre a
  `https://plataforma.ejemplo.local$request_uri`; en el 443 la IP tiene su propio bloque que
  redirige al nombre (con aviso previo del certificado, que no cubre la IP) y el bloque de la
  aplicación solo atiende el nombre.
- Un temporizador de systemd (`omniguard-redireccion.timer`, cada 5 minutos) ejecuta
  `/usr/local/sbin/omniguard-activar-redireccion`: cuando `getent ahostsv4` devuelva
  `10.10.11.10` para el nombre, sustituye el sitio (guardando el anterior como
  `omniguard.anterior-<fecha>`), pasa `nginx -t`, recarga y se desactiva solo. Registro:
  `journalctl -u omniguard-redireccion.service`.
- Para activarla **ya**, sin esperar al DNS del servidor (por ejemplo si los puestos ya lo
  resuelven): `sudo omniguard-activar-redireccion --forzar`.
- Para volver atrás: `sudo cp /etc/nginx/sites-available/omniguard.anterior-<fecha>
  /etc/nginx/sites-available/omniguard && sudo nginx -t && sudo systemctl reload nginx`.

Zabbix debe consultar `https://plataforma.ejemplo.local/salud.json` (por la IP recibirá un
`301` en cuanto la redirección esté activa).
